# Threats to validity (engineering observations for the research team)

These are recorded by the software side. They are not conclusions; investigating them is the research team's call.

| ID | Threat | Details and what Phase 1 does about it |
|---|---|---|
| TV1 | **Euler parameterisation dependence** | Euler sequences (and the rotation vector) differ from one another by bilinear second-order terms such as y·p, y·r and p·r, the same form as Model C's interaction terms. The parameterisation alone can shift effect from linear terms into apparent cross-axis interactions, especially when linear (asymmetric) coefficients are large. Euler interaction coefficients must **not** be read as anatomical coupling. Phase 1 preserves the full `q_WH` and `q_rel`, so alternative parameterisations (another Euler order, rotation-vector features) can be computed and compared before the model phase |
| TV2 | No torso reference | Head orientation relative to the tracking frame or neutral is not neck orientation relative to the torso. Torso motion cannot be distinguished (protocol §2.2) |
| TV3 | No magnetometer | No absolute heading on the Pro, and the heading at stream start is arbitrary. **G0 (untouched, on a table):** apparent drift 0.0012–0.0029 °/min (geodesic) over 5–10 min, and the z component, about the up axis, was the quietest. Worn drift, with movement and longer blocks, is not measured (O3) |
| TV4 | Undocumented SDK fusion filter | Smoothing, latency and bias handling are unknown. The SDK Euler order is undocumented. The SDK keeps `w ≥ 0`, so its quaternion sign jumps (handled).<br>**G0:** the output is strongly smoothed. Sample-to-sample change is about 3·10⁻⁵°; the residual is a slow, correlated wander (0.003° over 1 s), not white noise. The filter's latency is not measured. Direction and signs are verified (R6a/R6b) |
| TV5 | Timestamp resolution | 1 ms device timestamps floor interval-jitter estimates; the sample instant they refer to is undocumented |
| TV6 | Relative latency only | Host-arrival latency is relative (no shared clock). With the native shim, arrival times exclude Python scheduling. Python-side processing latency after the drain, which matters for later command timing, is a separate quantity and is not yet measured |
| TV7 | Device irregularities | **Duplicate timestamps:** 0.01–0.05% of samples, distinct samples arriving about 1 ms apart, kept invalid.<br>**Device-side pauses of about 300 or 600 ms:** the device produces no samples. They occurred in some handled sessions and once with the glasses untouched; they were not reproduced on demand, and the cause is unknown.<br>**A short gap (≈ 50 ms) 2–3 s after each (re)connect.** All are flagged and never silently used. A pause makes the gate stale |
| TV8 | Provisional parameters | All flag, gate and neutral thresholds are engineering defaults (see quality-and-metrics.md). `tau_stab_deg` is a placeholder (O6). Their values could affect which calibration attempts are accepted and should be frozen before comparative data collection |
| TV9 | Cable and connection sensitivity | Moving the USB cable at the PC end caused a full disconnect: an 11 s outage, the glasses power-cycled, and the device clock restarted (G0 R8). Worn use moves the cable. Pauses or disconnects during a block are possible; how a block handles them is O5 |
| TV10 | Achieved rate below the requested rate | Pose mode achieves 59.4 / 84.6 / 112.3 / 202.5 Hz for 60 / 90 / 120 / 240 Hz requested, with no loss. Any rate-dependent analysis must use the measured rate (`r_ref`), not the nominal |
| TV11 | Host suspension and late samples | After a PC sleep, a sample produced before the sleep arrived 29.9 s late, and a burst followed (G0 R9). The gate now measures staleness by data age, so such samples are stale. This assumes the host clock counts during sleep, as QPC did. Data collection should keep the PC from sleeping |
| TV12 | Fixture placement | G0 characterisation was done upright on a hard table, with a tilt of about 5° from the as-worn up axis, not on a head form. Intrinsic results (rate, jitter, drift) should not depend on this, but worn behaviour is not characterised (O3) |
